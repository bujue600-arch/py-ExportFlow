# D5 讲解：三态选择模型——bullet ④ 的前端核心与"语义的数学"

> 今晚代码：`features/assets/lib/selection.ts`（纯函数模型）+ `exportSubmit.ts`（幂等意图）+ `components/SelectionBar.tsx`（受控组件）。读完约 20 分钟。

## 1. 为什么 ID 枚举表达不了"全选"

列表 8721 条、接口上限 1000 条。"全选所有筛选结果"如果用 ID 枚举：①载荷直接超限；②用户翻一页勾一页也凑不齐。**全选不是"很多个勾选"，是另一种语义**——"满足这个筛选条件的全部"。所以模型必须能表达：

> 我要的是「这个筛选条件命中的所有条目」，除了这几条。

这就是三态模型的本质：`selectAll（语义层） + excludedIds（例外层）`，而不是 `explicitIds（枚举层）`的加长版。

## 2. 模型与不变量（selection-payload §2 的代码化）

```ts
interface SelectionState {
  selectAll: boolean;      // 全选标志
  explicitIds: Set<string>; // 显式勾选集（非全选模式）
  excludedIds: Set<string>; // 排除集（全选模式）
}
```

不变量：`selectAll=true ⇒ explicitIds 空`；`false ⇒ excludedIds 空`。

关键设计：**不变量由构造保证，不由约定保证**。看 `toggleRow`——它按 `selectAll` 分支决定动哪个集合，UI 拿到的 `SelectionState` 只能通过这组操作函数演进（加上 state 不可变更新），**不存在能构造出非法状态的代码路径**。测试里专门有一条"任意操作序列不破坏不变量"（`selection.test.ts` 最后一个 describe）。

对照面试语言：「我们把业务规则从'评审时注意'升级成了'类型与函数签名使违规不可表达'」。

## 3. 派生的纯函数（UI 只做展示）

| 函数 | 职责 |
|---|---|
| `isRowSelected` | 单行勾选态（全选 ? !排除 : ∈勾选集） |
| `deriveHeaderState` | 表头三态 all/some/none |
| `countSelected` | 全选=快照总数−排除数；否则=勾选数 |
| `isOverLimit` | >1000 拦截 |
| `describeSelection` | "已选全部 8720 条（排除 1 条）" |
| `buildExportPayload` | 组装 SELECTED_IDS / FILTER 载荷 |

`countSelected` 有个隐藏知识点：排除集元素**必来自快照命中集**（UI 只允许在快照筛选下排除），所以 `总数 − |excluded|` 是精确的，不需要求交集——这是把约束前置到交互设计，换取 O(1) 计数的例子。

`buildExportPayload` 复用 D3 的 `serializeFilter`：空筛选 → `{}`（今天契约 v1.1 刚澄清的"全量快照"语义——这个澄清来自 B 的 PR 评审，**契约是被实现推动演进的**，这本身就是规格流程的正常形态）。

## 4. 幂等意图：一个意图一个键

```ts
const intent = createExportIntent();   // 点「导出」时创建一次
intent.submit(payload, "csv");          // 网络重试内部复用同一 key
```

「意图」= 用户的一次导出决定；重试不是新意图，所以不换键。后端 `(key, payload_hash)` 唯一约束负责判重（D4 已实现），前端职责只是**别在重试时换键**。今晚测试还抓到一个 mock 陷阱：Response body 只能读一次，`mockResolvedValue(同一个Response)` 会让第二次 `.json()` 失败——mock 要 `mockImplementation(每次新建)`。

## 5. SelectionBar：受控组件的正确姿势

组件**不持有**选择状态：props 进（selection + snapshotTotal）、事件出（onToggleSelectAll/onExport）。状态在页面层用 `useReducer`/多次 `toggleRow` 管理，好处：①选择状态与分页/筛选状态同层，快照语义好维护；②组件测试不需要 mock 状态管理（5 个测试全是纯渲染断言）。

超限交互：显式勾选超限 → CSV/JSON 都可点但后端 1002？不——`isOverLimit` 时 JSON 禁用 + 提示文案，**前端先拦一道，后端 1002 是第二道**。双保险不是重复建设：前端拦的是体验（立即反馈），后端拦的是安全（绕过 UI 的调用）。

## 6. 面试官可能怎么问（附答题要点）

**Q1：跨页全选为什么不干脆把所有 ID 拉下来？**
要点：规模（万级）×上限（1000）下枚举不成立；全选是谓词语义（"满足条件的全部"）不是集合语义；排除集是有限例外，与谓词组合成完整表达；后端 FILTER 模式按条件重查——前后端对"选择"的理解在载荷契约上汇合。

**Q2：你的选择模型怎么保证不出现"既全选又有显式勾选"的脏状态？**
要点：不变量 + 由构造保证：状态只能经操作函数演进，函数内按模式分支维护对应集合；不可变更新；不变量专项测试。对比"用 useEffect 监听纠错"这种事后补救的坏味道。

**Q3（压力题）："前端拦了超限，后端为什么还要拦？你们不信任自己的代码？"**
要点：分层防御的对象不是"自己人"而是**入口**——UI 只是入口之一（还有脚本、重放、并发下的 TOCTOU：用户勾选时列表在变，前端计数可能已过期）；后端是唯一知道真实 total 的地方（FILTER 命中数必须服务端算）。信任边界讲清楚，比"防御性编程"四个字有说服力。

# D3 讲解：统一请求层与三层查询状态——bullet ③ 前端侧 + ⑤

> 今晚代码两块：`apps/web/src/api/client.ts`（统一请求层，88 行）+ `features/assets/`（筛选纯函数与草稿/已提交状态机）。读完约 20 分钟。

## 1. 统一请求层：UI 只面对一种错误（bullet ③ 前端侧）

### 1.1 全景图

```
组件 ──request<T>()──▶ fetch ──▶ 后端
                        │
             响应是信封？──否──▶ ApiError(5000)（防御：后端异常出口漏包/网关错误）
                        │是
             !ok 或 code≠0？──是──▶ ApiError(code, message, traceId)
                        │否
                     return data   ← 组件拿到的直接是 data 本体
```

三层归一在**一个函数**里完成，组件永远不需要写 `if (res.status === 4xx)` 这种分支——这是"前后端错误形状契约"（api-contract §2）的前端收益侧。

### 1.2 `isEnvelope` 类型守卫：信任但要验证

```ts
function isEnvelope(value: unknown): value is Envelope {
  // 逐字段检查 code/message/trace_id 的类型
}
```

为什么成功响应也要验形状？因为**契约靠人守就会漏**（昨晚后端就被 FastAPI 的 response_model 坑过）。类型守卫是"规格的可执行化"：TS 的 `value is Envelope` 叫 **type predicate**，通过后编译器自动把 `unknown` 收窄成 `Envelope`——对照你熟悉的 `typeof x === "string"` 收窄，这是它的对象版。

### 1.3 requestBlob：二进制错误体（简历原话的实现点）

下载的响应有两种形状（契约 §5）：成功是文件流，失败是信封 JSON。所以不能直接 `.blob()`：

```ts
if (res.ok) return res.blob();      // 成功：二进制
const text = await res.text();      // 失败：按文本读
// JSON.parse → 是信封 → ApiError；不是 → 兜底
```

**今天踩的坑（写进故事库）**：测试里用 jsdom 的 `new Blob(...)` 构造 Response，Node undici 的 Response 读它时数据损坏（`text()` 返回 `[object Blob]`）。原因：**jsdom 和 Node 各有一个 Blob 全局类，跨 realm 不兼容**。教训：测试环境的"假世界"和运行时的"真世界"有边界，构造测试数据要贴近真实来源。这类问题正是为什么简历写"FakeEventSource + 假时钟的**集成测试**"——测试基建本身就是工程活。

### 1.4 幂等键的伏笔

`newIdempotencyKey()` 用 `crypto.randomUUID()`（浏览器原生 API）。D4 创建导出时：**同一个意图**（用户点一次"导出"）生成一次，网络重试复用；点第二次生成新的。后端凭 `(key, 载荷哈希)` 判重。

## 2. 三层查询状态（bullet ⑤ 的实现）

### 2.1 为什么"输入即请求"是错的

键入每个字符都触发查询：①请求量与键入次数耦合（浪费）；②快速输入时多个请求并发，**旧响应可能后到覆盖新结果**（错序污染）。两类问题一个根：**把 UI 输入当成了查询条件**。

### 2.2 三层模型

```
draft（草稿）    FilterForm 的受控输入           ← setDraft 只改这层，永不发请求
committed（已提交）最近一次点「查询」的快照        ← query key 的一部分
mirror（镜像）   TanStack Query 缓存里的 data     ← 只被响应/SSE 更新
```

`useCommittedFilter` 就是 draft/committed 状态机（第三层 Query 替我们管）：

```ts
const submit = useCallback(() => setCommitted(draft), [draft]);
```

一行代码、语义重大：**提交是"快照"不是"引用"**——之后 draft 怎么变，已发出的查询不受影响。这份快照语义 D5 还会复用：三态全选的 `filterSnapshot` 就是它（面试时能讲出"复用"这层，说明设计是生长出来的）。

### 2.3 过期响应防御：两条路线（面试高频）

| 路线 | 机制 | 适用 |
|---|---|---|
| 手写取消标志 | `useEffect` cleanup 里把闭包里的 `cancelled` 置 true，回调里判断后再 setState | 裸 fetch / 面试手写 |
| Query 按 key 隔离 | 不同 committed 条件 = 不同 query key = 不同缓存条目，天然互不覆盖 | 本项目生产代码 |

本项目的请求走 Query 路线，但**今晚练习 1 要求你亲手写一遍取消标志**——它是简历原话，手写过才扛得住追问。

## 4. 面试官可能怎么问（附答题要点）

**Q1：统一请求层你们怎么设计的？错误怎么归一？**
要点：单一出口 request/requestBlob；三通道归一（非信封→5000、!ok 或 code≠0→ApiError、成功→data）；ApiError 携带 traceId，`toUserMessage()` 生成报障文案；下载双形状的处理。加分：讲 jsdom/undici 双 Blob 的坑。

**Q2：「输入不触发请求」怎么从结构上保证，而不是靠约定？**
要点：draft/committed 分层 + query key 含 committed——即使有人误把 draft 传进 hook，也只是"查询条件不对"，不可能"键入即请求"；约定靠人守，结构不靠人守。再讲快照语义与 D5 复用。

**Q3（压力题）：面试官说："防抖不就解决了？你这套三层是不是过度设计？"**
要点：防抖解决的是请求频率，解决不了两个问题——①语义错误（用户还没点查询，凭什么替他查？分页/导出需要"最近一次提交条件"，防抖后的条件是"最后一次键入"，两者不同）；②错序（防抖缩短窗口但并发依旧可能乱序，且翻页时不存在键入）。三层状态是语义正确性设计，防抖只是性能补丁，两者不互斥。

## 练习 1：mark_progress

```python
def mark_progress(session: Session, job: ExportJob, *, processed: int, total: int) -> ExportJob:
    """按已处理数计算进度百分比并推进（total=0 时进度恒为 0，不能除零）。"""
    progress = round(processed / total * 100) if total > 0 else 0
    return bump_and_publish(
        session, job,
        processed_count=processed, total_count=total, progress=progress,
    )
```

测试：

```python
def test_mark_progress_正常计算百分比(client, db_session):
    job_id = create(client, ids=["a1", "a2"], key="k-mp").json()["data"]["id"]
    job = db_session.get(ExportJob, job_id)

    job_service.mark_progress(db_session, job, processed=250, total=1000)

    detail = client.get(f"/api/export-jobs/{job_id}").json()["data"]
    assert detail["progress"] == 25
    assert detail["processed_count"] == 250
    assert detail["job_version"] == 2  # 创建1 → 进度2


def test_mark_progress_total为0_不炸且进度为0(client, db_session):
    job_id = create(client, ids=["a1"], key="k-mp0").json()["data"]["id"]
    job = db_session.get(ExportJob, job_id)

    job_service.mark_progress(db_session, job, processed=0, total=0)

    assert client.get(f"/api/export-jobs/{job_id}").json()["data"]["progress"] == 0
```

要点：

1. `bump_and_publish` 的 `**updates` 设计让扩展新入口不需要碰它——单一入口≠单一函数，是**单一通道**；
2. 除零是进度上报的经典线上事故（total 在 FILTER 统计前为 0），防御在最靠近计算的地方。

## 练习 2：事件序列结论

```
event: job_updated  data: {..., "status": "QUEUED",  "job_version": 1, ...}
event: job_updated  data: {..., "status": "RUNNING", "job_version": 2, ...}
event: job_updated  data: {..., "status": "FAILED",  "job_version": 3, "error": {"code": "3003", ...}}
```

版本为什么是 1→2→3：创建即版本 1（任务首次可观测）；worker 抢占翻 RUNNING 是第二次可观测变更；占位执行器落失败是第三次。**每次"外部能看到的差异"必须换一个新版本号**——如果两个事件共用一个版本，客户端的"旧版本丢弃"规则会把它们误判为重复，丢掉真实的状态变化。

附带观察：SSE 通道连接期间每 15 秒出现 `: ping` 注释行（心跳）；终端 1 的每条访问日志都带 `[trace_id]`。

## 1. 连接状态机：一张图讲完

```
        ┌──────────────── 页面隐藏：断连停一切；回前台：全新连接 ─────────────┐
        ▼                                                                      │
   connecting ──open──→ connected                                              │
        ▲                  │断连                                                │
        │ 1s/2s 退避        ▼                                                   │
        └──────────── (第3次连续失败) ──→ degraded：轮询(前台3s/后台15s)         │
        ▲                                     │ 同时以 5s/10s 退避继续重试 SSE  │
        └────────── 任一次重连成功 / online ────┘ 成功即升级、停轮询            │
```

**今晚的设计演进（面试好故事）**：v1.0 契约里"退避 1/2/5/10 封顶"和"3 次失败降级"是互斥的——第 3 次就降级的话 5/10 秒永远走不到。写测试时暴露，解法是**降级与重连并行**：轮询保进度不断，SSE 降级但不放弃，成功即升级。这叫"降级不是终点而是并行的备用通道"。契约已更新 v1.1——**规格是活的，矛盾被测试逼出来就修文档**，这正是规格流程的意义。

## 2. 为什么自己写 FakeEventSource

状态机的正确性 = 时序正确性：什么时候新建连接、隔多久重连、何时停轮询。真实 EventSource 的断连时机不可控，等真断网更不可能。FakeEventSource 做两件事：

1. **导演事件**：`simulateOpen/simulateError/emit/emitBye` 在测试里精确投喂；
2. **留档计数**：`instances` 按创建顺序记录每次连接——断言"退避期内没有新建连接"就是断言 `instances.length` 在特定时间点不变。

配合 `vi.useFakeTimers()` 的 `advanceTimersByTime(999)` / `(1)`，"1 秒退避"变成了精确到毫秒的确定性断言。**时序测试的通用配方：假的时钟 + 假的IO + 留痕的工厂**。

## 3. job_version 缓存更新（bullet ② 逐句落地）

简历原话拆解 → 代码落点：

| 简历原话 | 代码 |
|---|---|
| "单调版本号丢弃过期事件" | `shouldApplyEvent(known, incoming)`：严格大于才应用 |
| "setQueryData 跨所有分页×筛选视图精准更新" | 遍历 QueryCache，对每个 jobs list 缓存按视图语义更新 |
| "含条目移除与 total 重算" | activeOnly/状态筛选视图遇终态：条目移除 + `total-1` |
| "SSE 仅通知、HTTP invalidateQueries 校准" | 终态（结构性变化）后 `invalidateQueries` 兜底 |

两个关键细节：

- **乱序丢弃要"原样返回"**：`applyEventToPage` 对过期事件返回原 page 引用——引用不变，React/TanStack 直接跳过渲染与通知（和 D5 练习"no-op 返回原引用"同一原理，跨天呼应）。
- **setQueriesData 的坑**：它的 updater **拿不到 queryKey**，无法感知"这是哪个筛选视图的缓存"。解法：显式遍历 `queryClient.getQueryCache().getAll()`，逐个 `setQueryData`——多写五行，换来视图语义的完整表达。

## 4. React 集成（useJobUpdates）

```ts
useEffect(() => {
  const connection = createSseConnection({ url, onEvent, onSnapshot, pollActive, onPhaseChange });
  connection.start();
  return () => connection.stop();   // 卸载即断连：不留僵尸连接
}, [queryClient]);
```

依赖注入在这里闭环：生产传真 EventSource，测试传 Fake——**hook 本身零 mock**。页面生命周期（隐藏断连）已内建在状态机里，hook 只管挂载/卸载。

## 5. 面试官可能怎么问（附答题要点）

**Q1：断线自愈为什么不用 WebSocket？**
要点：场景是单向服务端推送（进度），SSE 足够且更简单（HTTP 语义/自动重连/文本协议）；双向需求（取消任务）才值得上 WS；EventSource 原生支持让浏览器管重连，但重连策略太粗（无退避封顶、无降级），所以要自建状态机——**用原生能力但把策略权拿回来**。

**Q2：乱序/重复事件怎么防？为什么放前端而不是信后端？**
要点：网络的本质决定重放/乱序不可根除（重连重放、多通道并存）；后端保证"版本严格单调+事件必带版本"（源头诚实），前端守卫（消费端防御）——两端各守一半，谁都不能裸奔。类比 CAS：版本号就是乐观锁的 expected。

**Q3（压力题）：轮询 3 秒一次，10 分钟就 200 个请求，你不觉得浪费？**
要点：算账——仅降级期间且仅活跃任务才轮询（`active_only` + refetchQueries type:"active" 只刷页面在看的查询）；正常态零轮询（SSE 推送）；后台 15s + 页面隐藏全停。**降级是异常路径的保底，不是常态**；再抛升级路径（WS/ETag/长轮询）说明知道边界。
